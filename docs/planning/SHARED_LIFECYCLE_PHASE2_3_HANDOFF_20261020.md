# Shared Account Lifecycle — Phase 2 + 3 Handoff (2026-10-20)

Status: **source + disposable-DB tests only.** Nothing was applied to the retained municipal DB or production. Parent design: `SHARED_ACCOUNT_LIFECYCLE_ARCHITECTURE_20261020.md`.

## What exists

**Phase 2 (identity)** — migration `20261019190644_SpaceIdentityAndLifecycle20261020` (additive, data-free):
- `SpaceRegistrations` (unique per tenant + kind + normalized number: "7" = "007"), `SpaceContractTerms`, `SpaceLifecycleEvents` (unique `(tenant, ClientOperationId)`, fingerprint, preview version).
- `ObligationAccounts`: nullable `SpaceRegistrationId`, `PredecessorAccountId` (unique per predecessor), `RetiredAtUtc`; tenant-composite FKs; check constraints.
- `btree_gist` exclusion constraint: two occupancies of one space can never share a day (inclusive end; open = infinity).
- Append-only triggers on events and terms (UPDATE/DELETE refused). DELETE is allowed only under the transaction-local `stalltrack.tenant_restore` switch set by `TenantRestoreRepository`; the three tables are in `TenantDataTables.Restorable` and the export.
- New monthly space accounts (create/import via `ObligationWorkflow`) are born with a registration. Existing accounts are NOT linked until the backfill is run.
- `SpaceIdentityPreflight` (read-only) and `SpaceRegistrationBackfill` (links only accounts alone on their normalized number; ambiguous groups are reported, never merged; idempotent; never run by migration or startup).

**Phase 3 (operations)** — `SpaceLifecycleWorkflow`, API `POST api/AccountLifecycle/{source}/{id}/preview` (Admin+) and `/execute` (SuperAdmin). Preview returns a state `Version`; execute needs `ClientOperationId` + that version. Same op id + same request replays; different request → `OperationConflict`; changed state → `StalePreview`.

| Action | Status by default | Rules |
|---|---|---|
| Resume (same holder, successor occupancy) | **Off** (`ResumeApproved=false`) | start = day 1, after closure month; rate in force at closure carried; no back-billing; predecessor untouched |
| Reassign (different holder) | **Off** | explicit holder + approved amount; same name needs confirmation; payor only by explicit in-tenant link |
| Renew (term evidence) | **Off** | open signed-contract account; must start the day after current term ends; appends a term, touches no rate/period |
| Retire (non-destructive) | **Off** | SuperAdmin; closed and zero balance over full history |

Fiesta/Araw lots are never eligible. Stalls are unchanged and have no executor on the shared contract.

## Correction (project-owner direction, 2026-10-20): rental accounts behave like rental accounts
Supersedes the Space-only policy and the "unavailable actions" screens above. Direction from the owner; it is NOT a recorded LGU financial rule and no Decision Registry entry was changed.
- **One rule table.** `LifecycleRules.ForSpace` is the single structural rule table for a monthly space, in the same shape and wording as a stall's `ForStall` (Admin or the Head Resume / Renew / Reassign; only the Head Close / Remove). `SpaceLifecycleWorkflow` calls it for state and role and adds only what needs a date, an amount or a balance. The read view (`SpaceAccountLifecycle`) and execution can no longer diverge. A unit test (`SpaceAndStallAgreeOnEveryStateTheyShare`) pins Resume / Renew / Remove agreement between stall and space; one difference is deliberate and documented there: a stall whose term has run out can be Removed while open, a space is closed first because it keeps billing monthly.
- **No per-LGU approval switch.** `SpaceLifecyclePolicy`, `SpaceLifecyclePolicies`, the `SpaceLifecycle:*` configuration and the "pending approval" reasons are removed. What blocks an action is the account's state, the actor's role, and the money. Specific cases stay blocked with a short reason (not a screen of explanations): a start not on the first of a month, a start inside the closure month, a renewal overlapping the recorded term, a missing approved amount, a same-name new holder without confirmation, and Retire while a balance is owed (a debt is never hidden).
- **Authority matches stalls.** Execute is Admin or Head; Retire is Head only (checked in the workflow).
- **Renew follows the stall rule:** an open signed-contract account whose recorded term has run out; a space-only occupancy has no term to renew. A late renewal is recorded as term evidence only (no rate, period or collection is touched).
- **Closure semantics.** `ActiveTo` in the future is "Ending": the account is active and billed to that date (`LifecycleState.Ending`, pill "Ends {date}"). Only an arrived end date is Closed: Closed Accounts lists only those, and Resume / Reassign / Remove are not offered before then. The source has no separate evidence of a manual closure vs a scheduled end, so the distinction is by date only; nothing was changed in the data. (The Space workspace register still filters and counts by `ActiveTo is null`; only its status label says Ending.)
- **UI.** `AccountLifecycleBar` replaces the large panel: a compact row of buttons under the profile header, the same component for stall and space profiles, drawing only server-allowed actions (an action waiting on the one-time space setup is a disabled button with a short tooltip). Closed Accounts space rows use the same compact icons as stall rows (View, Resume, Reassign, Remove) from one batched eligibility read; no panel under the row. The Space profile holds the lifecycle history as an ordinary "History" card; the holder is the account's own occupant, else its Business Payor, on the profile, the drawer and the lifecycle read.
- **Identity.** New monthly space accounts are created with their space. The four existing Cantilan working-copy accounts are still unlinked (backfill requires explicit authorization); "space not identified" appears only as that disabled tooltip until then.
- **Not changed:** approved rates, periods, collections/SRCs, OR/CT, arrears; NPM daily-billed flows; the stall commands.
